## P0

### P0-1 — Denylist is bypassable in ~105 documented ways (security)
- `internal/security/security.go:16-22` (`blockedBinaries` map),
  `:27-50` (`destructiveRmArgs`), `:118-182` (`IsBlockedCommand`),
  `:133-139` (wrapper stripping), `:171-178` (`chmod` case).
- Spec: `internal/security/fuzz_test.go` `blockedCommands` /
  `allowedCommands` + `TestIsBlockedCommandAdversarial`.
- Evidence: the adversarial test run above fails 105 subtests; the
  allowed table passes, so a fix must keep the allowed cases allowed.
- Bypass classes, each verified by a failing subtest:
  1. **`chmod` is dead code.** `blockedBinaries` has no `"chmod"`,
     so the `case "chmod":` at `:171` is unreachable (the
     `if !blockedBinaries[base] { continue }` at `:140` skips it
     first). `chmod 777 /etc`, `chmod -R 777 /`, `chmod -R 755 /etc`
     are all allowed. The fuzz table also requires recursive chmod of
     a system tree to be blocked even with a "safe" mode
     (`chmod -R 755 /`, `chmod -R 644 /usr`).
  2. **Long flags are invisible to the rm checks.** Both the
     recursive detection in `destructiveRmArgs` (`:32-40`) and the
     catch-all rm loop (`:153-157`) skip flags starting with `--`, so
     `rm --recursive /` and `rm --recursive --force /home` are
     allowed. (`--no-preserve-root` is checked, so that one variant
     is blocked.)
  3. **Wrapper stripping only strips a bare wrapper word.** The loop
     at `:133-139` strips `sudo`/`env`/`nice`/`time` and then takes
     the very next token as the binary. `sudo -u root rm -rf /`,
     `sudo -n rm -rf /`, `sudo FOO=1 rm -rf /`, `env FOO=1 rm -rf /`,
     `env -i rm -rf /`, `nice -n 5 rm -rf /`, `time -p rm -rf /`
     all pass: the next token is a flag or an assignment, not `rm`.
     `FOO=1 rm -rf /` (leading env assignment, no wrapper at all)
     also passes.
  4. **Missing wrappers / indirection entirely.** `su`, `doas`,
     `pkexec`, `runuser`, `nohup`, `setsid`, `timeout`, `command`,
     `stdbuf`, `busybox`, `toybox`, `xargs`, `eval`, `sh -c …`,
     `bash -c …`, `sh script.sh`, `bash -c 'echo hi'` are not in the
     map at all. `bash -c 'rm -rf /'` passes because the segment
     binary is `bash`.
  5. **Command substitution / backticks.** `tokenize` (`:66-116`)
     has no handling for `$(…)` or `` `…` ``, so
     `echo $(rm -rf /)`, `$(rm -rf /)`, `` echo `rm -rf /` `` pass
     (segment binary is `echo`).
  6. **Missing destructive binaries.** `mkfs.btrfs/.vfat/.ntfs/
     .exfat/.f2fs` (only `mkfs`, `mkfs.ext4`, `mkfs.xfs` are listed),
     `wipefs`, `sfdisk`, `cfdisk`, `sgdisk`, `truncate -s 0`,
     `cryptsetup luksFormat` are not listed.
  7. **`find` bulk delete / exec.** `find / -delete`,
     `find / -exec rm -rf {} \;`, `find / -exec chmod 777 {} \;`
     pass: `find` is not listed and `-exec` contents are never
     inspected.
  8. **Pipe-to-shell.** `curl … | sh`, `echo hi | bash`,
     `cat script.sh | bash` pass: the segment after `|` has binary
     `sh`/`bash`, which is not blocked.
  9. **Newlines are not segment separators, and backslash escapes
     merge tokens.** `tokenize` treats a real newline as plain
     whitespace (`security.go:66-116`) and `splitSegments` only
     splits on `;`, `|`, `&`, so `echo hi<newline>rm -rf /` is one
     segment headed by `echo` and passes — while `/bin/sh -c`
     executes the second line as a new command. Separately, the
     fuzz table's `\\n` / `\\t` cases are literal backslash
     sequences in the test strings (not real control characters):
     the tokenizer's backslash handling merges the escaped
     character into the preceding token (`rm\t-rf` becomes one
     token `rmt-rf…`), so `rm` never appears as a segment head and
     those cases also pass. The spec wants both refused.
- Suggested fix (owner: security): rewrite `IsBlockedCommand` to the
  fuzz-test spec — strip wrappers **with their flags/assignments**
  (`sudo [-u …] [-nEis]`, `env [-i] [-u …] [VAR=…]`, `timeout
  [duration]`, `nice [-n …]`, …), recurse into `$(…)` / backticks /
  `-c` string arguments / `-exec` arguments / pipe-to-shell
  (`| sh|bash|zsh|dash`), treat newline as a segment separator, add
  the missing binaries (`chmod` with recursive-or-777 rules,
  `mkfs.*`, `wipefs`, `sfdisk`, `cfdisk`, `sgdisk`, `truncate`,
  `cryptsetup`, `su/doas/pkexec/runuser/nohup/setsid/timeout/command/
  stdbuf/busybox/toybox/xargs/eval`, `find -delete/-exec/-execdir`),
  and match `--recursive`/`--force` long flags. Keep the allowed
  table green (`echo 'rm -rf /'`, `echo $(date)`, `chmod 644 file`,
  `sudo -l`, `find /tmp -name '*.txt'`, …). **Not fixed by this
  audit** — `security.go` is owned by a sibling.
- Note: `dd` is the one fail-safe case — the code at `:160-170`
  blocks *all* `dd` (the comment says otherwise-allowed, the code
  returns true unconditionally). Keep that behaviour; fix the comment.

### P0-2 — Telegram has no sender authorisation (messaging)
- `internal/messaging/telegram.go:384` (`Poll`): every incoming
  message with non-empty text is delivered to the handler
  (`App.Handle` → agent → tools, including `shell_exec` and
  `file_write`) regardless of chat/user. There is no allowlist
  anywhere in the repo (no config field, no gateway option, no
  check in `Poll` or `cmd/orion`/`cmd/oriond`).
- Anyone who discovers the bot username can drive the OS agent.
  Combined with P0-3 (unconfined file tools) and P1-10 (shell env
  leak), this is remote code/file access by design, not by accident.
- Suggested fix: add `telegram_allowed_chats: [int64]` to config,
  enforce it in `Poll` (drop + optionally log unauthorised chats
  before calling the handler), and add a test with two fake chats.
  **Not fixed** — `messaging/` is owned by a sibling.

### P0-3 — File tools have no path confinement (tools)
- `internal/tools/files.go:22` (`cleanPath` only does
  `filepath.Clean`; no allowlist, no symlink resolution, no `..`
  restriction) and the four tools that use it: `file_read` `:68`,
  `file_write` `:130`, `file_edit` `:188`, `file_list` `:256`.
- The agent can read/write any path the OS user can, e.g.
  `~/.orion/config.json` (Telegram token + API keys),
  `~/.ssh/id_ed25519`, `~/.bashrc`, `/etc/passwd`. `file_write`
  creates parent directories (`:146`) and overwrites arbitrarily.
- Suggested fix: confine to an explicit allowlist (workspace dir +
  data dir), resolve symlinks with `filepath.EvalSymlinks`, reject
  escapes, and add tests reading `~/.orion/config.json` /
  `/etc/passwd` by path. **Not fixed** — `tools/` is owned by a
  sibling.

### P0-4 — Anthropic rejects multi-tool-call turns (model + core)
- `internal/core/agent.go:260-270`: one `tool`-role message is
  appended per `ToolCall`.
- `internal/model/anthropic.go:82-124` (`toAnthropicMessages`): each
  `tool` message becomes its own `user` turn carrying one
  `tool_result` block.
- Anthropic's Messages API requires strictly alternating
  user/assistant turns, so two tool results in a row are two
  consecutive `user` turns → HTTP 400 on the next `Chat`, aborting
  the run. Any turn in which the model calls ≥2 tools fails on
  Anthropic (OpenAI accepts it, so this is provider-specific and
  invisible in OpenAI-only testing; the Anthropic test only covers a
  single tool result).
- Suggested fix: in `toAnthropicMessages`, merge all consecutive
  `tool` messages into a single `user` message whose content is the
  list of `tool_result` blocks (in order). **Not fixed** — `model/`
  is owned by a sibling.

### P0-5 — Ollama tool calls always have an empty ID (model)
- `internal/model/ollama.go:143`: `ID: ""` is hardcoded when
  converting Ollama tool calls.
- `internal/core/agent.go:266` then stores the tool result with
  `ToolCallID: ""`, and `toOpenAIMessages` /
  `toAnthropicMessages` emit a tool message with no
  `tool_call_id` / an empty `tool_use_id`, which the OpenAI and
  Anthropic APIs reject. Cross-provider history is therefore broken
  for any Ollama tool-call turn.
- Suggested fix: synthesise a stable ID when the provider omits one
  (e.g. `call-1`, `call-2` per turn, or a hash of name+arguments),
  in `ollama.go:143` or centrally in `core` when a `ToolCall.ID`
  is empty. **Not fixed** — `model/` is owned by a sibling.

## P1

### P1-1 — `RunStream` pays for (and can be corrupted by) a second provider call (core)
- `internal/core/agent.go:147-175` (`RunStream`) + `:178` (`run`):
  `run` first calls `provider.Chat` for the final turn, then
  `deliverFinal` calls `provider.Stream` with the same request.
  For Anthropic, `Stream` *is* a second `Chat`
  (`internal/model/anthropic.go:257`); for OpenAI it is a second
  HTTP call, and the OpenAI stream-fallback can make it a third
  (`internal/model/openai.go:335-343`). The second call may return
  different content (or tool calls, which are then silently
  ignored — see P1-2), and the user is charged twice.
- Suggested fix: make `RunStream` stream the final turn directly
  (one `Stream` call, no preceding `Chat` for that turn), or define
  the contract as "Chat decides tool-calls, Stream renders the
  final answer" and document the double call. **Not fixed** — `core/`
  is owned by a sibling.

### P1-2 — Streaming drops tool calls on every provider (model + core)
- `internal/model/openai.go:256-333`: `Delta.ToolCalls` is parsed
  (`openAIStreamChunk`) but never used; a streamed tool-call turn
  is delivered as (empty) text.
- `internal/model/anthropic.go:257-268`: `Stream` is a `Chat` whose
  `ToolCalls` are discarded; empty content returns nil, no error.
- `internal/model/ollama.go:170-228`: streamed tool calls are never
  parsed.
- Net effect via `core.RunStream`: a model that wants tools on the
  streamed turn gets its tool calls silently dropped and the run
  ends with an empty (or text-only) reply.
- Suggested fix: `Stream` must either return the tool calls
  (change the `Provider` interface) or return a distinct error when
  the streamed turn contains tool calls, and `core` must route such
  turns back through `Chat`. **Not fixed.**

### P1-3 — Streaming can return an empty reply with a nil error (model)
- `internal/model/openai.go:329-332`: valid SSE consisting only of
  empty deltas (role-only) yields `emitted==0`, `sawData==true`,
  `parseErrs==0`, so no fallback runs and `Stream` returns nil
  having delivered nothing. `core` then returns `""` with nil error
  and stores an empty assistant message.
- `internal/model/ollama.go:213-222`: the `chunk.Done` break is only
  reached after a non-empty content chunk, so a `done:true` chunk
  with empty content never breaks the loop — it waits for EOF or
  the context deadline.
- Suggested fix: OpenAI — fall back whenever `emitted==0`,
  regardless of `sawData`; Ollama — break on `Done` regardless of
  content. **Not fixed.**

### P1-4 — Shell output buffer is unbounded (tools)
- `internal/tools/shell.go:109-111`: `bytes.Buffer` grows without
  limit; the 64 KiB cap is applied only *after* `cmd.Run` returns.
  A command that floods stdout (e.g. `yes`) can exhaust memory
  before the 120 s timeout fires.
- Suggested fix: write through a capped writer (`io.LimitWriter`
  or a writer that kills the process past the cap) instead of an
  unbounded buffer. **Not fixed.**

### P1-5 — Shell inherits the agent's full environment, secrets included (tools)
- `internal/tools/shell.go`: `cmd.Env` is never set, so the child
  inherits `ORION_API_KEY`, `ORION_TELEGRAM_TOKEN`, etc.
  `shell_exec {"command":"env"}` prints them into tool output,
  which is fed to the model and can reach a Telegram user.
- Suggested fix: build a scrubbed env for the child (drop
  `ORION_*`, `*_API_KEY`, `*_TOKEN`, `*_SECRET*`) or set an
  explicit minimal env. **Not fixed.**

### P1-6 — `ActiveProvider` and `Validate` disagree on the effective model (config)
- `internal/config/config.go:253-266` (`ActiveProvider`): global
  `Config.Model` overwrites the per-provider model unconditionally
  (`:262-264`), contradicting the function's own doc comment
  ("per-provider model wins, else Config.Model") and contradicting
  `Validate` (`:89-150`), which computes the effective model as
  per-provider-wins. A config that validates can therefore run a
  different model than the one `Validate` checked.
- Suggested fix: make `ActiveProvider` match `Validate` (use the
  provider model when set, else the global one). **Not fixed** —
  `config/` is owned by a sibling (note: `TestActiveProviderModelOverride`
  in `config_test.go` currently asserts the global-wins behaviour,
  so the test and the doc comment cannot both be right — decide
  which is intended and fix the other).

### P1-7 — Saving config persists environment-supplied secrets to disk (config)
- `internal/config/config.go:183-226` (`Load`/`applyEnv`) +
  `:228-247` (`Save`): `Load` applies env overrides in memory, and
  any later `Save` — including `orion config set-provider` and
  `set-model` — writes the whole config, env-supplied API keys and
  Telegram token included, to `~/.orion/config.json`.
- Suggested fix: track which fields came from env and exclude them
  from `Save`, or make the mutating commands load without env
  overrides. **Not fixed.**

### P1-8 — Partial provider entries in a config file wipe the defaults (config)
- `internal/config/config.go:183-200` (`Load`): `json.Unmarshal`
  into the `Default()`-seeded map replaces a provider entry
  wholesale (Go map value semantics), so a file that only sets
  `providers.openai.api_key` zeroes that entry's default
  `Model`/`BaseURL`; `Validate` then fails with "no model
  configured". Users must repeat every default field to override one.
- Suggested fix: merge file entries over the defaults
  field-by-field after load (fill empty `Model`/`BaseURL` from the
  corresponding default entry). **Not fixed.**

### P1-9 — Subagent task contexts leak until their timeout (subagent)
- `internal/subagent/subagent.go:153-204` (`Spawn`/`runTask`):
  `Spawn` creates `ctx, cancel := context.WithTimeout(...)` at
  `:185` and stores `cancel` in the entry, but `runTask` never
  calls it on completion — the context (and its timer) lives until
  the per-task timeout (default 5 min) even for tasks that finish
  in milliseconds.
- Suggested fix: pass `cancel` into `runTask` and `defer cancel()`
  there. **Not fixed.**

### P1-10 — Finished subagent tasks are never evicted (subagent)
- `internal/subagent/subagent.go:194` (`m.entries[id] = entry`):
  nothing ever deletes from `entries`. `List`/`WaitAll`/memory
  grow without bound over a long daemon run.
- Suggested fix: evict finished entries (bounded LRU / TTL, or a
  `Forget(id)` API called by the CLI after `Wait`). **Not fixed.**

### P1-11 — `web_fetch` has no SSRF guard (tools)
- `internal/tools/web.go:73-…` (`webFetchTool.Execute`): any
  http(s) URL is fetched, including `http://localhost:11434`
  (Ollama), `http://169.254.169.254/` (cloud metadata),
  `http://localhost:2375` (Docker). No private/loopback/link-local
  block, no DNS-rebinding consideration.
- Suggested fix: resolve the host and deny loopback, private,
  link-local and multicast ranges (and re-check after redirects).
  **Not fixed.**

### P1-12 — Audit hash input is ambiguous (security)
- `internal/security/audit.go:38-53` (`computeHash`): fields are
  concatenated with no separator or length prefix. The comment
  claims field boundaries are fixed by their formats, but `actor`,
  `action` and `detail` are arbitrary strings — `("ab","c")` and
  `("a","bc")` hash identically, so moving characters between
  fields is undetectable.
- Suggested fix: length-prefix each field (or hash a canonical JSON
  encoding of the entry). Note this changes the hash format — bump
  the log format / handle old logs on reopen. **Not fixed.**

### P1-13 — `cmdTools exec` ignores the signal context (cmd)
- `cmd/orion/main.go:394`: `l.Tools.Execute(context.Background(),
  …)` — the main signal context (`main.go:31`) is not passed
  (and `cmdTools(args)` takes no context at all). Ctrl-C will not
  stop a running tool; a `shell_exec` can run its full 120 s
  timeout first.
- Suggested fix: thread `ctx` through `cmdTools` (and update
  `main_test.go` call sites). **Not fixed** — `cmd/` is owned by a
  sibling.

### P1-14 — CLI input loop is not cancellable while waiting for input (messaging)
- `internal/messaging/cli.go:60-88` (`RunCLI`): `scanner.Scan()`
  at `:74` blocks on stdin with no context awareness, so cancelling
  `ctx` (Ctrl-C via `signal.NotifyContext`) does not interrupt a
  waiting `orion chat` session until the user types a line or EOF.
- Suggested fix: read stdin in a goroutine and `select` on
  `ctx.Done()` between lines. **Not fixed.**

### P1-15 — `NewFileStore` chmods a pre-existing data dir (memory)
- `internal/memory/file_store.go:64-83` (`NewFileStore`):
  `os.Chmod(dataDir, 0o700)` at `:72` runs unconditionally, even
  when the directory already existed — including if the user points
  `data_dir` at `$HOME` or another shared directory, silently
  changing its permissions.
- Suggested fix: only enforce the mode on directories this call
  created (or when the current mode is more permissive than 0700
  and the dir is inside the expected tree). **Not fixed.**

## P2

### Core (`internal/core/agent.go`)
- **P2-1** `NewAgent` (`:60-90`) mutates the caller's `*config.Config`
  in place when filling `MaxSteps`/`TimeoutSeconds` defaults
  (`:77-82`). A shared config object changes under the caller (and
  under `App.Config`). Fix: copy the config before defaulting.
- **P2-2** `parseToolArguments` (`:303-314`) accepts any valid JSON,
  not just a JSON object (`[1,2]`, `123`, `null` all pass, then fail
  confusingly inside the tool). Fix: require the top level to be an
  object (or `null` → `{}`).
- **P2-3** `run` (`:178-…`): one `stepCtx` timeout covers the
  provider `Chat` *and* all tool calls in that step, so a slow
  `Chat` starves the tools (a 120 s tool timeout can get ~0 s of
  remaining budget). Fix: give tool execution its own timeout
  derived from the parent ctx, not the step ctx.
- **P2-4** `run`: `Agent.mu` is held for the whole run (up to
  20 steps × 120 s), so `SetLogger` and `Shutdown` block for that
  long. Acceptable serialisation, but `Shutdown` during a run
  cannot interrupt it — document it or use a separate
  `loggerMu` / shutdown flag.
- **P2-5** `run`: on "max steps exceeded" the partial progress
  (tool results already in memory) is discarded from the caller's
  point of view — the error carries no partial output. Consider
  returning the partial transcript alongside the error.
- **P2-6** `run` (`:201-204`): tool-call messages are stored in
  memory with the assistant's `Content` verbatim; a provider that
  returns `Content: null` (real OpenAI wire shape, covered by
  `e2e_test.go`) relies on Go's null-into-string behaviour — fine
  today, but fragile if the wire type changes to `any`.

### Model (`internal/model/`)
- **P2-7** `openai.go` usage fallback (Chat, ~`:247-252`): when
  `TotalTokens == 0` it overwrites even a reported non-zero
  `PromptTokens` with an estimate. Fix: only estimate the fields
  that are actually zero.
- **P2-8** `openai.go` `buildRequest` (~`:190-205`): `Temperature
  == 0` can never be sent explicitly (deterministic sampling is
  unrepresentable). Same pattern in Anthropic/Ollama builders.
  Fix: use a `*float64` / sentinel in `ChatRequest`.
- **P2-9** `openai.go` `Stream` (`:256-…`) and
  `ollama.go` `Stream` (`:170-…`): no retry on 429/5xx, unlike
  `Chat` via `doWithRetry`. A transient 429 mid-stream fails the
  whole turn. Fix: retry the stream setup (not mid-stream chunks)
  on retryable statuses.
- **P2-10** `anthropic.go:82-124`: the `default:` case
  (`:124-126`) passes unknown roles through verbatim; Anthropic
  only accepts `user`/`assistant` (plus extracted `system`), so a
  stray role (e.g. `""`) produces a 400. Fix: map unknown roles to
  `user` or reject them.
- **P2-11** `anthropic.go:108-116`: invalid tool-call JSON is
  silently replaced with `{}` when converting history back to
  Anthropic, masking malformed arguments. Fix: surface the error
  instead of substituting.
- **P2-12** `ollama.go:61-80` vs `:85-98`: asymmetry — responses
  are converted from object-form arguments, but requests are built
  with string-form arguments (`toOllamaMessages` sends
  `function.arguments` as a string) while Ollama expects an object.
  Fix: send the object form on requests too.
- **P2-13** `ollama.go:152-154`: `DoneReason` overwrites the
  `finish` value even when tool calls are present, so
  `FinishReason` says `"stop"` for a tool-call turn. Fix: only
  overwrite when there are no tool calls.
- **P2-14** `provider.go` `doWithRetry`: no `Retry-After` handling
  for 429 (fixed 100/200/400 ms backoff regardless); the 4 MiB
  response cap truncates large bodies and the resulting JSON error
  is misleading; network errors (DNS/TLS) are retried even though
  they will not self-heal. Fix: honour `Retry-After`, retry only
  retryable error classes, report truncation explicitly.
- **P2-15** `types.go` `CountTokens`: counts bytes/4, so non-ASCII
  text overestimates tokens. Minor; use rune count if it matters.

### Security (`internal/security/`)
- **P2-16** `scanner.go` `assignmentRe`: no word boundary, so it
  matches `token` inside `mytoken` and redacts the following value;
  values shorter than 8 chars are never redacted (short passwords
  slip through); the Telegram pattern requires exactly 35 chars
  after the colon and may reject future token shapes; JWT/Slack/
  generic high-entropy tokens are not covered.

### P2-21 — WONTFIX (reasoned)

Every mutation rewriting + fsyncing the whole `memory.json` is
kept as-is. Debounced/coalesced saves were considered and
rejected: the store's core contract is synchronous durability —
`TestKillRestartSurvival` proves every mutation survives a
`kill -9` with no graceful shutdown — and any debounce window
would break that guarantee (data written in the window would be
lost on a crash, with no `Close` to flush it). History is capped
at 200 messages, so a save is a small JSON rewrite + fsync, and
~3 writes per agent step is an acceptable durability price at
this scale. Revisit only if turn latency measurements show the
fsync is actually a bottleneck; the fix then is a write-ahead /
append-only journal, not a silent debounce.

### P2-22 — documented, not fixed in this package

The double report comes from `core.Agent.Shutdown`, which calls
`memory.Save()` and then `memory.Close()`, and each genuinely
re-attempts the save — so one underlying failure is reported
twice. Fixing it in the memory package would require `Close` to
swallow a save error (hiding a failed persist from callers that
only call `Close`) or to know the error was already reported,
neither of which the store can do soundly. `Close` deliberately
leaves the store open after a failed save so the save can be
retried; the idempotent-retry behaviour is now documented on
`FileStore.Close` in `file_store.go`. Deduping the report belongs
to the caller (`Agent.Shutdown` — out of this worker's scope).
