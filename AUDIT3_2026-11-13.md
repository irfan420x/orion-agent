**Mount/namespace-escape probes were REMOVED by stop order** (Audit 3,
2026-11-13): the mount probes (`mount --bind`, overlay, tmpfs over
`/tmp` paths) were shadowing the host's `/tmp` — almost certainly via
shared mount propagation — and breaking live writes for the running
oriond and for shells on this VM (see §6, environment incidents).
Namespace creation is proven blocked at the syscall level by
`TestSeccompLauncherBlocksSyscalls` instead. Mount probes must only
ever run inside a fully private mount namespace, with a before/after
check that the host mount table is untouched.

## 7. Close-out fixes (this phase)

Two defects were found by the close-out's own verification runs and
fixed here; neither weakens a test.

### 7.1 TestAdversarialPrivilegeEscalation (was the one red test)

**Root cause, corrected.** The first diagnosis (seccomp filter
unavailable because the test binary runs from a temp dir and the
launcher lookup looks next to the running binary) was WRONG, and the
log line it rested on was a red herring:

- The test wires the launcher in explicitly (`advConfig` →
  `testLauncher`, which builds `orion-seccomp` from source once per
  run). `TestAdversarialSeccompFilterReallyOn` passes with the filter
  count at ambient+1 — the filter IS installed for these probes.
- The "seccomp filter unavailable (no orion-seccomp launcher binary
  found…)" line comes from `Available()`'s probe: `runProbe` builds a
  bare `Config{Enabled: true, Root: …}` with no launcher, and
  `Prepare` → `setupSeccomp` logs the warning once per process.
- The actual failure was the final assertion,
  `strings.Contains(out, "Operation not permitted")`: no command in
  the probe ever emits that literal string. `hostname` prints "you
  must be root to change the host name"; the init_module probe
  printed the errno as a NUMBER (`ret=-1 errno=1`).

**Fix** (`internal/sandbox/adversarial_test.go`,
`internal/sandbox/sandbox.go`):

1. The python init_module probe now prints the strerror too —
   `INIT-MODULE ret=-1 errno=1 (Operation not permitted)` — so the
   assertion matches real EPERM evidence. The existing `errno=1`
   check still passes. The test still requires EPERM failures; it
   does not require less.
2. The test's comment claimed sethostname is "blocked by the filter".
   A control experiment (throwaway test, deleted afterwards) proved
   otherwise: `hostname` fails IDENTICALLY with and without the
   filter — the UTS namespace is created by the clone in the outer
   user namespace, where the process holds no privilege. The comment
   now says what is true (namespace/capability containment, not
   filter action), and the test now runs a no-filter control
   asserting `HOSTNAME=1` without the filter, so it can never again
   be misread as a filter proof. The filter itself is proven live by
   `TestAdversarialSeccompFilterReallyOn` and
   `TestAdversarialSeccompGaps`.
3. `runProbe` now sets `DisableSeccomp: true`: the availability
   probe checks namespace/chroot availability only; the filter is a
   separate layer validated by `probeSeccompLauncher` at setup time.
   This also stops the misleading warning from polluting production
   logs (oriond calls `Available()` on the shell path).

### 7.2 TestAdversarialCPUSpin — real data race (test-only)

`go test -race` found a genuine data race: the test read
`spinBuf.String()` while the spin command was still running and
os/exec's stdout-copy goroutine was still writing to the same
`strings.Builder` (not safe for concurrent use). Fixed by waiting
(`spinCmd.Wait()`, which returns only once copying has completed)
before reading the buffer; the deferred `Wait` was removed. No
product code is involved — the race stack is test code + stdlib
exec internals, and the product's shell_exec buffering passed the
race suite. Sandbox race package now passes with 0 data races.

### 7.3 Race re-run contaminated by the VM write flap

A full race re-run failed 39 tests across `internal/security` and
`internal/tools` — every failure an `operation not permitted` write
to a `/tmp` temp dir during a flap window, 0 data races. Environment,
not code; re-run clean (see §1).

## 9. Environment incidents (not Orion bugs)

- **`/tmp` write flap (09:25–09:29, 09:43–09:47, 10:55, 11:15–11:17
  SGT, ongoing, intermittent)**: writes to `/tmp` (and at times
  `~/workspace`) flap between working and EPERM on a seconds-to-
  minutes timescale: files are created 0-byte, then the content
  write fails with `operation not permitted`. Reproduced by the
  parent's own shell, outside Orion, with the sandbox disabled and
  the same user namespace as oriond. Host `/tmp` is two stacked
  uid-mapped tmpfs mounts. The likely cause of the 09:25–09:29
  episode is Audit 3 Workstream 2's mount probes shadowing `/tmp`
  via shared mount propagation (see §3); the later episodes have no
  mount activity behind them and are a property of this VM. On a
  normal laptop `/tmp` this does not occur. The flap also cost test
  runs: one full race run failed 39 tests to it (§7.3), and a
  single-package race run failed at setup writing `_testmain.go`.
- **`/dev/null` missing (10:09–10:12 SGT)**: `/dev/null` vanished
  from /dev (tmpfs); `mknod` fails EPERM (no CAP_MKNOD in this user
  namespace); `go build` failed because the compiler opens
  /dev/null for build IDs. Worked around with `unshare -rm` +
  bind-mounting a file over /dev/null in a private mount namespace.
  The runtime restart at 10:41 restored it (`crw-rw-rw-`).
- **Live config truncated (10:55 SGT)**: the P1 coordinator's config
  edit hit the flap mid-edit and truncated `~/.orion/config.json`
  to 0 bytes. The DeepSeek key and Telegram token live ONLY there.
  The parent restored it at 11:02 SGT (temp-file + verify + atomic
  rename, mode 0600) from the values Irfan sent in chat, and
  live-verified both (Telegram getMe ok, DeepSeek /v1/models ok).
  oriond PID 2971 was never restarted and kept serving from the
  config in memory. No secret values appear in this report, in any
  doc, log, or commit. Lesson recorded: config edits must always go
  through temp-file + verify + atomic rename, and a `.bak` next to
  the live config would have made this a non-incident.

## 10. New findings for the next phase

- **F-A3-1 (P2, seccomp-missing fail-open)**: when the sandbox is
  enabled and the filter is not disabled, but no `orion-seccomp`
  launcher can be found (or the probe/install fails),
  `setupSeccomp` logs a warning once and the command runs with
  namespace/chroot containment but NO syscall filtering. The P1
  phase closed fail-open for sandbox *unavailability* and *setup
  failure*, but the missing-launcher path is still graceful
  degradation by design. The next hardening phase should treat an
  enabled-but-unfilterable sandbox the same way: refuse unless an
  explicit opt-out is set — or at minimum surface it per-command,
  not once per process. Do not redesign here; recorded for the
  next phase.
  - **FIXED 2026-11-13 (post-audit hardening phase, unreleased):**
    the missing-launcher path is now fail-closed, on the P1
    pattern. `setupSeccomp` returns an error wrapping the new
    `sandbox.ErrSeccompUnavailable` sentinel (naming the missing/
    unusable launcher and the opt-in), `Prepare` propagates it,
    and `shell_exec` refuses the command (`denied`) and runs
    nothing — unless the operator explicitly opts into unfiltered
    runs with the new `sandbox.allow_without_seccomp=true`
    (default false), in which case every degraded run is logged
    (per command, naming the opt-in), or disables the filter
    outright with `sandbox.disable_seccomp=true` (a deliberate
    choice, never a refusal). The two opt-ins govern different
    degradations and neither implies the other: a missing filter
    is refused even with `sandbox.allow_unsandboxed_fallback=true`
    (that opt-in covers a sandbox that cannot be established at
    all; letting it run the command fully unsandboxed would be a
    worse degradation than sandboxed-without-filter). The
    availability probe is unaffected — it runs with the filter
    disabled, so it never logs a misleading missing-filter
    warning. Tests: `TestSeccompMissingLauncherRefused`,
    `TestSeccompMissingLauncherOptInRuns`,
    `TestSeccompDisabledRunsWithoutLauncher`,
    `TestPrepareWithDisabledSeccompLogsNoWarning`,
    `TestShellExecSandboxRefusesWithoutSeccompLauncher`,
    `TestShellExecSandboxSeccompOptInRunsDegraded`,
    `TestShellExecSandboxDisableSeccompRuns`,
    `TestShellExecSandboxSeccompFallbackComposition`; docs updated
    in `SECURITY.md`, `README.md`, `CHANGELOG.md` ([Unreleased]).
- **F-A3-2 (P2, observability)**: no pprof/debug endpoint on oriond;
  goroutine leaks are not directly observable (threads are the
  proxy). A localhost-only debug endpoint (or an explicit
  opt-in) would close this.
- **F-A3-3 (P3)**: no full fresh-install run record survives (see
  §6). Do one clean-HOME install.sh run before any release.
- **F-A3-4 (P3)**: the 24–72h daemon soak was not achieved in this
  phase. The live daemon keeps running and the sampler keeps
