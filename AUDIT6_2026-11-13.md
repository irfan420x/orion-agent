# Audit 6 — Fresh-eyes audit of Orion v0.2.0-rc10

**Date:** 2026-11-13 (SGT)
**Commit audited:** `376e56d798e98020be6c18b7992171df1943bb8d` (tag `v0.2.0-rc10`)
**Auditor:** Muse (Audit 6 coordinator + 5 workers), fresh eyes on rc10
**Scope:** rc10's fixes for all 9 Audit 5 P1s (F-A5-1..F-A5-9) and all 38 Audit 5 P2s (F-A5-P2-1..P2-38), the version-string nit, rc8 security regression, full test suite + race, one live DeepSeek proof (scratch config only), docs freshness.
**Constraints honoured:** live daemon (PID 77142, rc10) not touched; `~/.orion/config.json` never read or modified; no live Telegram turn sent; nothing committed, tagged, or pushed (rc10 was pushed separately by the parent at 18:06 SGT, server-verified main = `376e56d`, tag `v0.2.0-rc10` = same SHA, MIT LICENSE commit included).

## Verdict: NOT production-ready

**0 P0, 3 P1, 21 P2.** The rc10 fixes are real and extensive — 6 of the 9 Audit 5 P1s are genuinely fixed, 31 of the 38 P2s are genuinely fixed, the suite is green, and the live DeepSeek proof passed — but three things block production:

1. **`/compress` is still completely unmetered (F-A6-1)** — the 4th leg of F-A5-5, claimed fixed in rc10, has no production caller passing the metering sink. A chat at its daily limit can run `/compress` repeatedly for free.
2. **Two shipped Telegram entrypoints run ungated (F-A6-3)** — `orion daemon` and `orion telegram poll` never call `SetPermissionGate`, so destructive/network tools run without approval on those paths. Pre-existing since rc8, not an rc10 regression, and the live daemon is `oriond` (so no live exposure) — but the gate does not hold everywhere it is advertised to.
3. **The 24–72 h soak (F-A3-4) is still open** — the longest single daemon run ever is ~1 h 39 m; the rc10 daemon had been up ~22 min at audit time. F-A3-2 (no pprof/debug endpoint) is also still open.

In addition, the skill delimiter — the core of the F-A5-8 fix — is bypassable by the exact marker string it delimits (F-A6-2), and the suite itself is not deterministically green: `TestAdversarialNamespaceDeathKillsAll` failed 4 of 6 runs in this audit (a timing race, not a code bug), and the known `TestSubagentManagerEndToEndUsageAndIsolation` flake recurred. None of the P1s is a one-line safe fix except where noted; all need the fix plans in §3–§4.

## 3. P1 findings (3)

### F-A6-1 (P1) — `/compress` is still completely unmetered — the F-A5-5 leg claimed fixed but not fixed

**What rc10 did.** `compressWithOn` gained a `provider.Sink` parameter (`internal/app/chats.go:759-773`), and `AutoCompact` passes its real sink (`:743-752`); extraction metering also got a sink (`:1034-1052`). Tests claim `TestCompressWithOnMetering` passes, and W3's replay of it passes.

**The hole.** No production caller passes the sink on the `/compress` path. `internal/app/chats.go:776` (`handleCompress`) and `internal/app/commands.go:663` (`/compress` dispatch) call `compressWithOn` without a sink — only `TestCompressWithOnMetering` passes one. The method documents the sink as the metering contract, and the contract is never fulfilled on the only path that matters.

**Reproduction (W3, in a scratch harness).** `handleCompress` with a 1500-token summarisation; the injected `Budget.Usage(111)` reads **0** afterwards — i.e. `/compress` spends provider tokens that are never metered, never priced, never checked pre-flight, never surfaced to the cost tracker. On the live Telegram path a chat already at its daily limit can run `/compress` repeatedly for free; this is exactly the F-A5-5 class the rc10 coordinator claimed closed.

**Fix plan.** Thread the real sink into `handleCompress` and the `/compress` dispatch in `commands.go:663`; add a `TestHandleCompressMetering` that asserts `Budget.Usage(chatID)` increments after a real `/compress` (not just `compressWithOn` with a hand-passed sink). Audit the other callers of `compressWithOn` for the same omission.

### F-A6-2 (P1) — Skill END-marker injection defeats the F-A5-8 delimiter — no code-level bar on body-directed end/switch

**What rc10 did (real).** The skill body is now delimited (`===== BEGIN SKILL "X" CONTENT =====` / `===== END SKILL "X" CONTENT =====`); the prompt adds a hierarchy instruction; docs state the restriction is anti-drift, not a security boundary; a mismatched `END SKILL "Y"` is refused. Tests `TestPromptContainsSkillDelimiters`, `TestSkillBodyDelimiters` pass.

**The hole.** rc10 checks the footer marker only when a *different* skill is being activated. A skill body containing a line exactly equal to its own end marker — `===== END SKILL "sneaky" CONTENT =====` — is **not** validated (W4 confirmed: `parseSkillBody` has no check that the body contains no marker line, and the `sanitizeSkillBody` in `internal/skills/loader.go:113-126` rejects no delimiter patterns). A malicious skill body can close its own delimiter early and inject a fake footer plus fresh instructions; the only remaining defence is the prompt's hierarchy instruction, which is advisory. The same gap applies to the activation header: the loader has no code-level bar on a body-directed `END SKILL` followed by `BEGIN SKILL "other"` + `Activate` — the model is told to refuse it, but nothing enforces it.

**Reproduction (W4).** Crafted a skill whose body contains the exact end-marker line, then the injected text; `parseSkillBody` accepted the body and `sanitizeSkillBody` returned it unchanged. The model-side hierarchy instruction is a prompt, not a barrier.

**Fix plan.** In `loader.go`/`parseSkillBody`, reject any skill body containing a line that parses as a `BEGIN SKILL`/`END SKILL` marker (or escape/neutralise such lines on load); add a regression test with the exact marker line in the body. Consider also rejecting bodies containing `Activate` directives. Note the threat model: skills are operator-installed, so this is third-party-skill risk, not operator-risk — but the delimiter was the fix's core mechanism, and it is bypassable by the exact string it delimits.

### F-A6-3 (P1) — `orion daemon` and `orion telegram poll` run Telegram turns ungated and unisolated

**What rc8 did (still holds on oriond).** The permission gate is wired in `cmd/oriond/main.go:193, 197-203` and applied per-chat (`internal/app/chats.go:233-234, 381-399, 685-686, 969-970`).

**The hole.** The two other Telegram entrypoints never call `SetPermissionGate`: `cmd/orion/main.go:757–814` (`orion daemon`) and `:741–749` (`orion telegram poll`). `orion telegram poll` additionally uses the global `a.Handle` (`internal/app/app.go:419`), bypassing the per-chat isolation (`chats/<chatID>/`) that P1-O3 established. Pre-existing since rc8, not an rc10 regression — but the live daemon being `oriond` is the only reason there is no live exposure. Anyone running `orion daemon` (advertised as the equivalent daemon path) gets destructive and network tools without any approval prompt.

**Reproduction (W5, code audit).** `grep -rn SetPermissionGate cmd/orion/main.go` returns nothing; the gate is set only in `cmd/oriond/main.go` and in tests. No runtime repro was needed — the wiring is absent.

**Fix plan.** Extract the gate wiring into a shared `wireGate` helper called by `oriond`, `orion daemon`, and `orion telegram poll`; make `orion telegram poll` use the per-chat handler (or delete it as a duplicate of `oriond`). Add a test that asserts every command path that starts a Telegram loop has a non-nil gate. Decide whether `orion daemon` and `oriond` should be merged (they are near-duplicates now).

## 4. P2 findings (21)

### F-A6-P2-1 (P2) — Single-shared-token check accepts degenerate summaries (F-A5-2 residual)

`internal/app/compact.go:586` (`verifySummaryContent`): any single shared token passes, so a summary of the word "project" repeated 200 times passes ("1 token shared") — W1 reproduced it in the harness. **Fix:** require ≥2 distinct shared tokens (or ≥3, matching the earlier W1 design), and/or add a minimum information-density check (distinct content words / length).

### F-A6-P2-2 (P2) — One giant message defeats the summariser input cap (F-A5-2 residual)

`compact.go:585`: the cap is enforced per *message* (each message truncated to ≤1000 tokens), not on the whole input — one message of 20,004 tokens is handed to the provider even though the cap is 16,000 (W1 repro). **Fix:** truncate or split the assembled `SummariserInput` to the 16,000-token cap after truncation; the cap must bound the total input, not each message.

### F-A6-P2-3 (P2) — Summariser prompt ships raw content to the provider; summary stored unredacted (P2-8 residual)

`compact.go:585` builds the summariser prompt from the raw transcript prefix with no redaction, so the provider call contains whatever secrets/keys are in the transcript. The stored summary is also unredacted (`compact.go:587`). The transcript leg is now fixed (P2-8), but the summarisation leg is not — the same exposure class, one hop away. **Fix:** run the summariser input through `RedactSecrets` before the provider call, and redact the stored summary before writing it to `summaries.jsonl`.

### F-A6-P2-4 (P2) — Overlong (>16 MiB) lines are skipped but never counted as corrupt (P2-3 NEW bug)

`internal/app/transcript.go:431` and `:480`: `readLine` returns `nil` for an overlong line, so `Load` skips it silently — it is never counted as corrupt (`transcript.go:450`). **Fix:** make `readLine` return a sentinel (or count the skip) so `Load` increments the corrupt counter; add a regression test with a >16 MiB line.

### F-A6-P2-5 (P2) — Migration remainder permanently blocked once a session does anything (P2-4 partial)

`internal/app/transcript.go:700`: `MigrateFrom` returns `(0, nil)` if any non-`Migrated` message or non-message record exists — a single compaction summary, or any live message, permanently blocks the remaining `legacy.jsonl` remainder. **Fix:** allow migration to proceed with a summary (treat it as a boundary), or make `MigrateFrom` idempotent by skipping already-migrated records instead of refusing the whole remainder.

### F-A6-P2-6 (P2) — Mid-turn budget check never sees subagent spend (F-A5-6 residual)

The mid-turn check (`internal/app/chats.go`, `checkBudgetMidTurn`) reads only the global agent's `Usage`; fetched subagent results are charged to the global agent, not to the per-chat agents, so the check is blind to child spend during a turn. A turn spawning 4 children can blow the budget mid-turn and is only caught at turn end. **Fix:** charge fetched subagent results to the per-chat agent's usage before the mid-turn check, or make the mid-turn check sum the global + per-chat usages.

### F-A6-P2-7 (P2) — Timed-out subagent tasks are never charged; tasks finishing after the last turn are never charged (F-A5-7 residual)

The rc10 sweep charges `Done`/`Failed` unfetched tasks, but timed-out tasks (which still spent provider tokens before timing out) are never charged, and a task finishing after the last turn is never charged. **Fix:** charge timed-out tasks on sweep (they spent tokens); charge late-finishing tasks on the next turn's sweep or at session close.

### F-A6-P2-8 (P2) — `Resolve`/timer race narrowed to microseconds, not closed (P2-20 residual)

`internal/permissions/permissions.go:110-111, 143-145`: the window is now microseconds and a 3,000-iteration stress found 0 mismatches — but the race is still there by construction (timer expiry vs `Resolve` is a race, not an ordered hand-off). **Fix:** make `Resolve` cancel the timer under the same lock (or use a single `sync.Once`-style state transition so only one of timer/Resolve can win).

### F-A6-P2-9 (P2) — `### Tools` level-3 heading silently ignored (P2-25 residual)

`internal/skills/skills.go` requires the `## Tools` heading at level 2; a `### Tools` heading is silently ignored, so a skill author who nests the section gets no tool list and no error. **Fix:** warn on (or accept) a level-3 `Tools` heading; add a regression test.

### F-A6-P2-10 (P2) — Skill hardlink loads; `parseFile` Lstat-then-Open TOCTOU (P2-26 residual)

`internal/skills/loader.go:113-126` uses `Lstat` refusal, but a hardlinked skill file still loads (same inode, different name), and `parseFile` does `Lstat` then `Open` — the file can be swapped between the two calls. **Fix:** check `nlink > 1` and refuse (or resolve the inode), and open-then-`fstat` instead of `Lstat`-then-`Open`.

### F-A6-P2-11 (P2) — Enum match short-circuits all other validation (P2-27 NEW bug)

`internal/tools/validate.go:179-186`: if a schema field has an `enum` and the value matches one enum entry, `validate` returns success immediately — pattern, bounds, and type checks are never run. A schema with `enum: ["a","b"]` + `pattern: "^[0-9]+$"` accepts `"a"` (which violates the pattern) and any value that matches the enum regardless of the other constraints. **Fix:** validate enum membership as one constraint among others, not as an early return; add a regression test with enum + pattern/bounds.

### F-A6-P2-12 (P2) — Symlinked `DataDir` falsely refused by planning `ensurePlanningDir` (P2-34 residual)

`internal/planning/planning.go:34`: the symlink refusal does not resolve `DataDir` first, so a legitimately symlinked data dir is refused. **Fix:** `filepath.EvalSymlinks` the data dir before the refusal check (and re-check the resolved path).

### F-A6-P2-13 (P2) — `Close()` landing inside `Start()` leaks the MCP server process forever (NEW, reproduced)

`internal/mcp/client.go`: `Close` sets `closed=true` and returns early when `cmd==nil` (nothing to kill yet). If `Close` lands after `Start` sets `starting=true` but before `cmd` is assigned — a window spanning the whole `prepareSandboxed` (ms) for sandboxed servers — `Start` proceeds: `cmd.Start()` succeeds, the handshake fails on the already-closed client (`initialize: mcp: client closed`), and `Start`'s failure path calls `Close()` again, which is a no-op because `closed` is already true. **Nothing ever kills the server.** Repro (W2, overlay test, since deleted): poll for `starting==true && cmd==nil`, call `Close()`, wait — server PID still alive after 3 s, `waitCh` never closed. Reproduced twice (PIDs 130268, 143592; second run under `-race`). Reachability is low in production (`Manager.Close` only runs after `StartManager` returns), but a daemon shutdown during startup can hit it, and each leak is a live process + open pipes + goroutine. **Fix:** make `Close` during `starting` wait for `Start` to finish (or record a pending kill that `Start` honours after `cmd.Start()`).

### F-A6-P2-14 (P2) — Sandboxed MCP servers share `/work` with `shell_exec`: read + write (NEW, reproduced)

Both use `sandbox.DefaultConfig(dataDir)` → the same root `<dataDir>/sandbox` (`internal/mcp/sandbox.go:sandboxConfig`; `internal/app/app.go:122,295` → `tools.go:59` for shell). W2's sandboxed probe **read** a file planted in `<dataDir>/sandbox/work` (`WORKDIR-SECRET-PLANTED-BY-SHELL`, simulating a file a shell turn left there) and **wrote** `planted-by-server.txt`, which appeared on the host. The "can never read the agent's config/keys/home" claim holds, but `/work` is shared mutable state across all sandboxed servers and shell commands: a malicious server passively reads anything shell turns leave in `/work` and can plant files a later `shell_exec` might run. **Fix:** per-server work dir (e.g. `<root>/work-mcp-<name>`) or document the sharing.

- README has no MCP-confinement or per-chat budget/USD-cost section.

### F-A6-P2-16 (P2) — Version string still says rc9 (process)

`internal/version/version.go:8`: `const Version = "0.2.0-rc9"` while the tag is `v0.2.0-rc10`. The binary is rc10 code (commit `376e56d`) but reports rc9 — see §1.3 for the root cause (`Makefile:26–29`, `install.sh:95–103` set only `Commit`/`BuildDate` via ldflags; a `const` cannot be overridden). **Fix:** change `Version` to a `var` and set it at build time from `git describe --tags` in both Makefile and install.sh; add a release-checklist item (or a CI check) that `orion version` matches the tag. The version-mismatch is a release-process bug, not a runtime bug — but it already caused one misdiagnosis in this audit cycle (the version string is the first thing anyone checks).

### F-A6-P2-17 (P2) — `TestAdversarialNamespaceDeathKillsAll` fails ~2/3 of runs (test reliability)

Coordinator runs: full suite FAIL, isolated FAIL, isolated PASS, `-count=3` FAIL/FAIL/PASS — **4 fails / 2 passes (67% failure rate)**. The test is timing-dependent (launcher "seccomp filter unavailable" lines in the output; `pids` file missing). Not a code regression — but a suite that fails 2/3 of the time on a security test cannot be trusted as a gate, and it masks real regressions. **Fix:** make the test deterministic (wait for the launcher to be ready before asserting, or mark the timing-dependent part as a separate, retried check); do not weaken the assertion.

### F-A6-P2-18 (P2) — `TestSubagentManagerEndToEndUsageAndIsolation` flake recurs (known)

The same test flaked in Audit 4, Audit 5, and now Audit 6 (`internal/app`: "max steps exceeded" under parallel load; passes 3/3 on re-run). It is a test-only timing issue, but it recurred in three consecutive audits and is now the single most common reason the suite goes red. **Fix:** give the test a deterministic step budget (or a retry) and track it as a known-flake with a ticket, not as a surprise each audit.

### F-A6-P2-19 (P2) — MCP prompt injection residual (delimiters advisory, no system-prompt warning)

`internal/mcp/tool.go:delimitMCPResult` brackets results and neutralises inner markers; `TestMCPResultDelimiting` passes. But the delimiters are advisory to the model — there is still no system-prompt warning that MCP-originated text is untrusted, the same residual Audit 5 noted. **Fix:** add a system-prompt line marking MCP results as untrusted third-party data (or, stronger, strip instruction-shaped content from MCP results before injection).

### F-A6-P2-20 (P3, noted) — `ScrubEnv` is name-based only

A secret-shaped *value* under an innocuous env name (`MY_NOTE=sk-audit6-fake-…`) reached the sandboxed server intact (W2, verified by an in-code assertion; the `<redacted>` in the test log was display-layer redaction, not code). The same scrub is shared with hooks/shell, and the daemon's env normally holds no secrets (config is file-based), so this is low-severity defence-in-depth only. **Fix (optional):** value-shape redaction in `ScrubEnv` (e.g. `sk-…`, `ghp_…` patterns) as well as name-based.

### F-A6-P2-21 (P3, noted) — Near-cap line stream burns CPU, not memory

Ten 15 MiB invalid-JSON lines are dropped with bounded memory (+16 MB heap), but there is no rate limit: a server streaming near-cap lines indefinitely keeps `readLoop`/`handleLine` busy. Low. **Fix (optional):** rate-limit or back off on repeated near-cap invalid lines.
