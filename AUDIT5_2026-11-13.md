## Verdict: NOT production-ready

**0 P0, 9 P1, 38 P2.** The rc9 feature set is real and largely works — all 9 gaps are implemented, the suite is green, and the live DeepSeek proof passed — but three things block production:

1. **Two MCP findings are security-relevant and daemon-threatening:** MCP servers run completely unconfined (F-A5-4 — a malicious server reads the config's DeepSeek key and Telegram token and exfiltrates, bypassing every control that binds built-in tools), and a newline-less flood bypasses the 16 MiB line cap and OOMs the daemon (F-A5-3).
2. **The budget is not a budget:** side-channel provider calls (memory selector, auto-compact, extraction, /compress) are unmetered (F-A5-5), the check is pre-flight-only so one turn can overspend without limit (F-A5-6), and unfetched subagent results are never charged (F-A5-7). Spend can exceed the daily cap by a large multiple while `/usage` reports less.
3. **The 24–72 h soak (F-A3-4) is still open** — the longest single daemon run ever is ~1 h 39 m; the rc9 daemon had been up ~25 min at audit time. F-A3-2 (no pprof/debug endpoint) is also still open.

In addition, auto-compaction — the feature built to stop silent history loss — still silently drops history in two reachable states (F-A5-1) and never verifies the summary that is supposed to preserve it (F-A5-2); and a skill body can escape its own tool restriction at will (F-A5-8). None of these is a one-line safe fix except where noted; all need the fix plans in §3–§4.

## 3. P1 findings (9)

### F-A5-1 — FIFO cap still silently drops working history with no summary once the breaker trips, or when pressure is >2× budget

`internal/core/compact.go:301-319` + `internal/memory/file_store.go:142-144`. `maybeAutoCompact` is the only thing standing between history growth and the 200-message FIFO cap in `FileStore.AddMessage`, and it runs only at turn start (`agent.go:517`). Two states disable it: breaker tripped (returns without touching history) and `pressure > maxAutoCompactPressure (2.0)` (deliberately skips summarisation). In both states every subsequent turn's `recordMessage → AddMessage` silently drops the oldest turns — no summary fact, no warning, no transcript summary record. The transcript retains the raw turns (working-history/recall loss, not absolute data loss), but it is precisely the silent-loss path the file header claims to close.

**Proof (worker repro, overlay tests):** real cap-enforcing `memory.NewEphemeralStore` seeded with 195 turns, summariser always errors → breaker trips after 3 calls → 3 more turns. Result: history pinned at exactly 200, the seeded first turn ("my favourite number is 17") is gone, and **no `conversation-summary` fact exists**. Same outcome at ~39× pressure (summariser called 0 times). Test gap that hid it: every existing compact test uses `fakeStore`, whose `AddMessage` has **no 200-cap at all** — the compaction↔FIFO interaction is entirely untested.

**Fix (fuller plan):** (a) bounded emergency summarisation — summarise a truncated slice of the oldest turns even when over budget, instead of skipping entirely; (b) on tripped breaker, spill dropped turns to an explicit per-session "dropped, unsummarised" record surfaced loudly in `/status` and the card; (c) at minimum log FIFO drops with the dropped turn count. Regression tests: the two repro tests above, against `EphemeralStore`/`FileStore`, not `fakeStore`.

### F-A5-2 — Summary content is never verified; garbage summaries are accepted, and even a good summary barely reaches the model

`internal/core/compact.go:340-357`. The only checks before `ReplaceMessages` drops the prefix are non-empty and the `FilterExplicitSave` gate. No check that the summary preserves anything from the source (no token overlap, no fact-preservation check, no minimum-information check). A provider returning filler such as `"Nothing durable was discussed."` passes the gate, is stored, and the prefix is dropped. `compact_test.go`'s own fake summariser returns exactly that string as its fallback — the test suite itself demonstrates a content-free summary flowing through as valid.

Compounding gaps: the summariser prompt (`compact.go:~L407`, identical in `compressWithOn`, `commands.go:662`) says "Preserve facts, decisions, names, numbers" but never mentions pending approvals, todo/checklist state, open questions, or user instructions/preferences (todos and approvals are safe for other reasons — PlanningStore files, 90 s gate expiry — but open questions and user instructions in the dropped prefix depend entirely on the model volunteering them). And even a perfect summary is weakly surfaced: it lives in the `conversation-summary` fact (capped at 8000 runes) and recall (`recall.go:108-132, L52-55`) only injects a fact if it shares ≥1 content token with the current query, truncated to **200 runes per item, max 3 items** — an 8000-rune summary is effectively invisible except for the matching 200-rune fragment.

**Fix (fuller plan):** cheap preservation check (reject summaries sharing no content tokens with the source, or below a length floor relative to input); extend the prompt to name pending items, open questions, and user instructions; always inject the latest summary section or raise the recall cap for the `conversation-summary` fact specifically. Regression test: a summariser returning `"Nothing durable was discussed."` (or zero token overlap) must refuse the compaction and leave history untouched.

### F-A5-3 — MCP `readLoop` 16 MiB line cap is bypassable: newline-less flood grows memory unboundedly (OOM the daemon)

`internal/mcp/client.go:91-94` promises `maxLineBytes` (16 MiB) stops "a flooding server" exhausting memory. `readLoop` at `:411-414` does `line, err := r.ReadBytes('\n')` and only checks `len(line) > maxLineBytes` **after** `ReadBytes` returns. `bufio.Reader.ReadBytes` → `collectFragments` accumulates full 64 KiB buffers with no limit and only returns on newline/EOF/error (verified in Go 1.27.4 stdlib source).

**Proof (stdlib-only repro, no MCP server executed):** a pipe fed 40 MiB with no newline — after 1.5 s `ReadBytes` was still blocked with heap 34.8 MiB; it returned only at EOF with `len=41943040`. A malicious/compromised MCP server streaming without `\n` OOMs the daemon (VM has ~700 MiB free) before the cap ever fires. Newline-terminated floods *are* capped, so this is specifically the newline-less path.

**Fix (fuller plan):** replace `ReadBytes` with a bounded read (e.g. `ReadSlice` loop that kills the server once accumulated bytes exceed `maxLineBytes`, or `io.LimitedReader`). Regression test: fake-server mode writing >16 MiB without a newline, asserting the client dies promptly with bounded memory. No such test exists today.

### F-A5-4 — MCP server processes run completely unconfined: they bypass the sandbox, file confinement, and egress controls that bind built-in tools

`internal/mcp/client.go:322` (`Start`) execs the server directly — no seccomp launcher, no chroot, no `confinePath`, cwd is the data dir. Built-in file tools *are* path-confined (`internal/tools/file*.go`: `confinePath`, `~/.orion`, `~/.ssh` denied roots) and `shell_exec` is sandboxed. An MCP server runs as the daemon uid with full filesystem access: a compromised or supply-chain-malicious server can read `~/.orion/config.json` (DeepSeek key, Telegram token), `~/.ssh`, and exfiltrate over the network — none of which any built-in tool can do. The per-call permission gate (`ClassNetwork`, `gate.go:113`) does not cover this: the server acts in the background between/around approved calls, and the user approving `mcp__fs__read_file` cannot see the server also reading the config.

**Fix (fuller plan):** run MCP servers under the same sandbox launcher as `shell_exec` (seccomp + namespace confinement), or at minimum document MCP servers as fully-trusted code equivalent to hooks, and consider a per-server allowlist. Mitigating fact: servers are operator-installed via `~/.orion/mcp.json` only (no repo/chat influence), so this needs a malicious server binary, not a malicious prompt.

### F-A5-5 — Unmetered provider calls bypass the budget entirely: memory selector, auto-compact, extraction, /compress

`internal/core/recall_v2.go:524-548`, `internal/core/compact.go:430-448`, `internal/core/extraction.go:216-235`, `internal/app/commands.go:676` — each calls `provider.Chat` directly and **discards `resp.Usage`**. Turn usage accumulates only in the main loop (`internal/core/agent.go:646-648`), and the side calls run outside it (selector + auto-compact before the loop, `agent.go:517`; extraction in a background goroutine, `extraction.go:129-159`). So none of these tokens reach `TurnFinished` → never in `Budget.RecordUsage` (`chats.go:463-472`), footer, or `/usage`.

**Proof by code path + magnitude:** auto-compact's input is the whole dropped history prefix (tens of thousands of tokens; the rc6 incident showed one turn carrying a 96,929-rune feed), output capped 800; the selector runs **every turn with typed memories** (manifest + input as prompt); extraction runs every 5 turns/10 tool calls. A chat can spend thousands of unbudgeted tokens per day while `/usage` reports less — and a chat already at its limit still gets these calls for free, since the pre-flight check happens after recall/compaction in the same turn.

**Fix (fuller plan):** accumulate these calls' `resp.Usage` into the turn's usage (thread a usage sink through `defaultMemorySelector`/`defaultCompactionSummariser`/`defaultSessionExtractor`, or record them directly to the chat's `Budget` in `runChatTurn` via a per-run collector). Regression test: scripted provider returning known usage from the selector/compactor, assert `TurnFinished.Usage` includes it.

### F-A5-6 — Budget is pre-flight-only with `Check(chatID, 0)`: one turn can blow the budget without limit, no mid-turn stop

`internal/app/chats.go:438` — the only `Budget.Check` call in production passes `tokens=0`, i.e. it only refuses a turn if the chat is *already* over. `RecordUsage`'s over-limit error is deliberately swallowed (`chats.go:463-472`: "the turn already ran, and the NEXT turn is the one that gets refused").

**Proof:** limit 100,000, chat at 99,999 used → `Check(…,0)` passes; a single RSS-heavy turn (cf. rc6: one turn legitimately cost ~59k tokens before calibration) records ~160,000 used — 60% over budget, with no abort. The budget as implemented is a *next-turn* gate, not a cap on spend. (The `Check(chatID, tokens)` signature exists precisely for a projected-cost check, but no caller ever supplies a projection.)

**Fix (fuller plan):** either estimate the turn's input tokens up front (history + input token count, which the calibrated counter can now do) and `Check` that projection, or enforce a mid-turn abort when cumulative usage crosses the limit. The cheap mitigation is documenting that the budget is a soft/next-turn control, which the current doc comments do not state plainly.

### F-A5-7 — Subagent tokens are counted only if the parent fetches the result; spawn-and-never-fetch spends invisibly

`internal/tools/subagent.go:335-352` — the *only* sink call site (`:348`, `t.set.sink.AddSubagentUsage(res.Usage.Tokens)`) is inside `subagent_result`, guarded by a `delivered` map so a second fetch doesn't double-count (good). But a result never fetched is never charged (comment admits this), and timed-out tasks record zero usage. The child executor genuinely spent the tokens (`internal/app/subagent.go:134-179`, fresh child agent, full provider run).

**Proof:** `subagent_spawn` (maxConcurrent 4, `app.go:189`) → child runs a multi-step turn → parent never calls `subagent_result` → `AddSubagentUsage` never fires → `TurnFinished.SubagentTokens` is 0, footer shows no subagent tokens, `Budget.RecordUsage` sees only the parent's tokens. Repeatable every turn: up to 4 children × full turns of spend, all off-budget and off-`/usage`.

**Fix:** charge on spawn completion, not on fetch — e.g. have the Manager invoke the sink when a task reaches Done/Failed (the `delivered` guard can move to the Manager), or have `runChatTurn` sweep finished-but-unfetched tasks at turn end. Medium fix with an obvious regression test (spawn, don't fetch, assert `TurnStats.SubagentTokens > 0`).

### F-A5-8 — A skill body can escape its own `## Tools` restriction at will; the restriction is not a security boundary against skill content

`internal/core/skills.go:165-171` — `skillAllows()` always allows `"skill"` itself, even while restricted. `internal/tools/skill.go:150-156` (`action:"end"`) + `internal/core/skills.go:271` (`clearActiveSkill()`) then lift the restriction unconditionally. Switching to an unrestricted skill does the same (`skills.go:197-212`, replace on invoke). Worse, the product *tells* the model to obey the body: `internal/tools/skill.go:64-67` ("read them and do what they say"), `internal/core/skills.go:96` ("you must follow them"). And `internal/tools/skill.go:177-196` (`formatSkillBody`) returns the body **verbatim, undelimited**, followed by the footer `[Skill "x" is now active…]` — a body can contain a fake copy of that footer, fake tool results, or fake system text, and the model has no way to distinguish body from framework text.

**Proof (worker repro, scratch copy):** fake provider playing a model that obeys the body: call 1 invoke `adder` (Tools: echo only) → call 2 `skill end` (offered while restricted) → call 3 `other` runs, `other.callCount()==1`. Existing tests already prove the primitives (`TestSkillEndLiftsRestriction`, `TestSkillSwitchReplacesRestriction`); no test covers a body that *instructs* the escape.

**Fix (fuller plan, design decision):** either (a) treat skill content as untrusted data — delimit the body in the tool result, add a system-prompt instruction that skill text is data not instructions, and forbid the body from directing `skill end`/skill-switch/tool choice; or (b) document `Tools` as anti-drift only, not a security boundary, and warn on installing third-party skills. The delimiter + hierarchy instruction is the cheap part; the end/switch policy is the design decision.

### F-A5-9 — Glob `**` matching is exponential; unbounded pattern, no ctx check in the matcher

`internal/tools/search.go:516` — `matchGlobSegments` recurses over every split for each `**`; `validateGlobPattern` (`:487`) caps nothing (no length/segment limit). It runs once per walked entry (up to 20k), and the walk's ctx check (every 256 entries) cannot interrupt a single match call. Tool ctx timeout is 120 s (`core/agent.go:323`).

**Proof (worker repro, probe in copied tree, 12-deep tree, one `x.go`):** pattern `**/*.go` 2 ms; 4×`**` 65 ms; 8×`**` 25 ms; 12×`**` 614 ms; **20×`**` = 42.6 s for a single match**. A deeper tree or more stars exceeds the 120 s tool timeout and stalls the turn.

**Fix (small + obvious regression test):** collapse consecutive `**` segments (semantically identical) in `validateGlobPattern`, cap pattern runes (e.g. 512) and segment count, or rewrite the matcher iteratively with memoisation. Recommend collapse + cap as the immediate fix. Repro: `glob {"pattern": "<**/>×20*.go", "path": "<12-deep dir>"}`.

## 4. P2 findings (37)

### Compact + transcripts (F-A5-P2-1 … P2-8)

**F-A5-P2-1 — Transcript summary-append failure is silently swallowed; the drop proceeds anyway.** `internal/core/compact.go:261-274, 348-357`. `recordSummary()` returns nothing — on error it only logs. The header comment claims "Either persist failing aborts the compaction with history untouched", but that is false for the transcript leg: `appendSummaryFact` → `recordSummary` (failure ignored) → `ReplaceMessages`. If the transcript append fails (disk full, permissions), the prefix is dropped and the transcript — the claimed unbounded backstop — silently lacks the summary. Proof (overlay repro): sink whose `AppendSummary` always errors, good summariser → `history=12 transcriptMessages=2 transcriptSummaries=0`. **Fix (one-line-ish + regression test):** make `recordSummary` return `error` and abort the compaction before `ReplaceMessages` when it fails.

**F-A5-P2-2 — `CompactionStatus.Pressure` is stale after a successful compaction; `/status` and the footer lie.** `internal/core/compact.go:285, 361-366`; surfaced at `internal/app/chats.go:725-735`. `c.pressure` is set at turn start and never recomputed after `ReplaceMessages` succeeds. Proof (overlay repro): 30 turns compacted to 12 messages, `Compactions=1`, yet `Pressure=1.59` — `/status` prints "1 auto-compaction(s), history 159% full" for a history that is actually ~6% full. **Fix (one-line-ish):** recompute `c.pressure = HistoryPressure(recent, budget)` after a successful drop.

**F-A5-P2-3 — One >4 MiB transcript line makes the whole session unloadable.** `internal/session/transcript.go:scanLocked (~L262)`, `Records() (~L367)`: `bufio.Scanner` with max token 4 MiB. A single overlong line makes `Open()` **and** `Records()` return `bufio.Scanner: token too long`. `Open` failing means `wireChatTranscript` logs and the agent runs with **no transcript at all** — subsequent turns are never recorded, and the session cannot be resumed. Tool results are capped at 256 KiB, so the realistic vector today is a huge CLI paste/`orion run` piped input. Proof (overlay repro): one valid message + one 5 MiB JSON line → both fail with `token too long`. **Fix (small):** replace the scanner with a `bufio.Reader` loop (or raise the cap substantially) and treat an overlong line as one corrupt line to skip.

**F-A5-P2-4 — Migration failure mid-way is unrecoverable; the remainder is never imported.** `internal/session/transcript.go:MigrateFrom (~L424)` + `internal/app/sessions.go:38-79`. `MigrateFrom` appends per-message with fsync; on the first error it returns `(0, err)` — but the messages already appended stay, so `t.count > 0` on every later open and the "import once" guard permanently blocks retrying the remainder. `openOrCreateTranscript` then returns the error, `wireChatTranscript` logs it, and the agent runs without a transcript. (Also: all migrated records share one timestamp — the `memory.json` mtime — since `model.Message` carries no timestamp; and migration only imports `RecentMessages(0)`, i.e. at most the last 200 turns.) **Fix (small but needs design):** make migration resumable — e.g. record a migration marker/progress, or on open, if the transcript holds only `Migrated` records and the store holds turns not present, import the remainder.

**F-A5-P2-5 — Resume silently drops summaries, silently caps at 200, and never reports corrupt lines.** `internal/app/sessions.go:ResumeSessionForChat (~L145)` + `internal/session/transcript.go:Messages() (~L397)`. (a) `Messages()` excludes `KindSummary` records and resume never loads `Summaries()` into the fact or context — summaries that exist only in the transcript are invisible after resume. (b) `ReplaceMessages` caps the restored history at 200 with no warning when the transcript holds more. (c) `CorruptLines()` is never read by any app/core caller (zero consumers outside tests). Note the `conversation-summary` fact is also shared across sessions of one chat, so resuming an old session mixes in summaries from other sessions. **Fix (small):** surface `CorruptLines()` in the resume result/message; warn when the transcript exceeds the 200 cap; load transcript summaries into the working context or fact on resume.

**F-A5-P2-6 — No locking across Transcript handles/processes: duplicate seqs, migration double-import race.** `internal/session/transcript.go:Transcript.mu` serialises only one object. Proof (overlay repro): two `Open()` handles on the same file, one append each → seqs `1, 1`. Same hazard across processes: `oriond` and a CLI `orion run` share the same `DataDir`/sessions dir with no `flock`. `O_APPEND` single `write()` calls don't interleave mid-record for small records, but seq/count drift, and `MigrateFrom`'s check-then-act (`count==0` → import) can double-import if two processes open simultaneously. Also `appendLocked` decrements `seq` on write/sync/close failure even though the bytes may already be on disk — a later append can reuse the seq. **Fix (small):** `flock` the transcript file on open/append (or enforce single-owner discipline and document it); don't decrement `seq` after a write that may have landed — re-scan instead.

**F-A5-P2-7 — Warning band is skipped on a one-turn jump; breaker has no auto-recovery.** `internal/core/compact.go:294-300, 311-319, 373-390`. (a) The warning fires only when pressure is measured inside `[0.70, 0.80)` at turn start; a single giant paste/tool result jumping pressure from 0.69 to ≥0.80 compacts with zero advance notice (the compaction event itself is shown, so this is minor). (b) The breaker never re-arms on its own — no time-based retry, no retry after N turns. A transient provider outage (the documented DeepSeek 60 s stall) tripping it 3 times disables auto-compaction for the rest of the session; only a successful manual `/compress` (same provider — fails while the provider is still down), `/resume`, or `/new` resets it. Also the summariser sends the whole old prefix as one user message with no size trim, so a prefix in the 0.8–2.0 band can exceed the provider context and fail on its own. **Fix (small):** re-arm the breaker after a cooldown with a logged retry; consider a warning when pressure jumps over the band.

**F-A5-P2-8 — Privacy: secrets are persisted verbatim in an append-only, never-compacted transcript; no scrubbing on the transcript path.** `internal/session/transcript.go:AppendMessage` stores the full `model.Message` including tool-call arguments verbatim (the round-trip test asserts calculator arguments survive byte-for-byte). Scrubbing exists only for process env (`tools/shell.go:scrubEnv`) and hook/display text (`messaging/redact.go:RedactDisplayText`) — nothing on the transcript path. File/dir perms are correct (0600/0700) and per-chat isolation holds, so the exposure is no worse than `memory.json` today — except retention: `memory.json` is bounded and compacted, while the transcript is append-only and keeps every secret-bearing turn forever (a pasted key, a shell command containing a token, a `file_read` of a config). Summarisation also ships the full prefix to the provider, unredacted. **Fix (small):** apply `security.RedactSecrets` (or an equivalent) to message content/tool arguments on transcript append, or explicitly document the retention and add a transcript-prune path.

### Hooks + MCP (F-A5-P2-9 … P2-17)

**F-A5-P2-9 — No cap on tools-per-server or on tool-schema size: definition flood to the model.** `internal/mcp/client.go:620` (`ListTools`) appends every advertised tool; `normalizeInputSchema` passes `properties`/`required` through verbatim (only the description is capped at 2000 runes). A server advertising thousands of tools, or one tool with a multi-MB schema (bounded only by the 16 MiB line), gets all of it injected into every provider request — context/cost flood. Contrast `maxHooksPerEvent = 32` in hooks. **Fix (small):** cap tools per server (e.g. 64, skip+log extras) and cap serialized schema bytes.

**F-A5-P2-10 — Hook JSON decision: the *first* JSON-parseable stdout line wins, even if it carries no decision.** `internal/hooks/hooks.go:663-676`: the loop `break`s on the first line that unmarshals into `hookOutput`, regardless of whether `decision` is empty. Repro: hook prints `{"status":"ok"}` then `{"decision":"block","reason":"no"}`, exits 0 → the block is swallowed and the tool runs. (Exit 2 still blocks, so only the exit-0 JSON path is affected.) Decision matching is also case-sensitive (`"Block"` is treated as unknown, warn-and-continue). **Fix (near one-liner):** only accept a line whose `decision` field is non-empty, compare case-insensitively.

**F-A5-P2-11 — Hook fail-open on clean non-zero exit.** `PreToolUse` (`hooks.go:426` ff.): signal death / timeout / start failure fail **closed**, but a clean exit 1, 3, 127… is continue-with-warning. A buggy hook (`set -e` script failing on a missing dep, exit 1) therefore silently stops enforcing policy while tool calls proceed; the operator only gets a log line. This is a deliberate design choice, enshrined by `TestPreToolUseOtherExitContinuesWithWarning`. **Fix:** policy decision needed — either fail closed on any non-zero exit, or keep it and log loudly at startup/daemon level. Not a one-line safe fix because it changes documented behaviour and an existing test.

**F-A5-P2-12 — Dead MCP server leaves a zombie and stale tools; no deregistration.** `readLoop` calls `markDead` on EOF/error/oversize line but never `cmd.Wait` — `Wait` runs only in `Close()` (`client.go:720`), so a server that dies mid-turn becomes a zombie until daemon shutdown, and its tools stay registered: the model keeps calling dead tools (each fails fast with the death error, fed back as tool-result text). No restart loop (good — no respawn storm), but also no health re-check. **Fix:** reap in `readLoop` (goroutine `cmd.Wait()` after death) and deregister the server's tools / surface them as unavailable.

**F-A5-P2-13 — Sequential MCP startup can stall daemon startup.** `manager.go:72` (`startOne`) runs servers one by one on `context.Background()`; each can burn ~20 s (10 s initialize timeout + 10 s list timeout) before the next starts. N slow/misbehaving servers delay daemon readiness linearly. **Fix:** start servers concurrently and/or add a total startup budget.

**F-A5-P2-14 — PreToolUse hook stdin is not redacted, while block reasons are.** Hook payloads carry raw model arguments (`hooks.go` `PreToolUse` marshals `args` verbatim). A secret the model pasted into an argument (e.g. a token in a `shell_exec` command) reaches the hook unredacted, and a verbose hook that logs stdin to a file leaks it — inconsistent with the redaction applied to block reasons and tool results. Low value as a finding (a hook is already arbitrary code as the daemon uid and can read `config.json` directly), so defence-in-depth only: redact `arguments` the same way before handing them to the hook.

**F-A5-P2-15 — `Alive()` lies for a never-started client.** `client.go:212`: `Alive()` returns `deadErr == nil`, which is true before `Start` ever runs. Only used in tests today, but any future health/status use would misreport. **Fix (one-liner):** return `started && deadErr == nil`.

**F-A5-P2-16 — MCP prompt-injection surface is unmitigated (residual).** Server tool descriptions (capped 2000 runes) and tool results are fed to the model verbatim apart from secret-redaction and truncation (`registry.go` choke point). A malicious server can put instructions in a description or a result ("ignore previous instructions…", fake tool results). This is the same class as `web_fetch` results, so not a code bug — but MCP servers are external processes with unknown capabilities, and Orion has no delimiting, quoting, or system-prompt warning for MCP-originated text. Flag as residual risk; mitigation is a larger design item (delimit MCP content in the transcript / warn in system prompt).

**F-A5-P2-17 — `Client.Start` double-start race (latent).** `client.go:322`: the `started` check-then-set is not atomic (lock released between check and set). Two concurrent `Start` calls could both launch the server. Single caller in practice (`Manager.startOne`, sequential), so latent only. **Fix:** hold the lock across the check-and-set or use `sync.Once`-style guard.

### Cost / budget / approval (F-A5-P2-18 … P2-23)

**F-A5-P2-18 — `/usage` cost is priced at the *current* model for the whole day's tokens.** `internal/app/commands.go:323-353` (`UsageLineForChat`) prices `DayUsage` (prompt/completion/subagent totals for the whole UTC day) via `cost.EstimateTotals(providerName, modelName, …)` using `chatProviderInfo` — the chat's *current* provider/model. `budget.Budget` stores no per-model split (`internal/budget/budget.go`, `chatDay` has only totals). Proof: chat uses `deepseek-chat` all morning (~100k tokens ≈ $0.03), then `/model` switches to `claude-opus-4` ($15/$75 per 1M) → `/usage` reprices the morning's DeepSeek tokens at Opus rates (≈ $7.50) — a ~250× overstatement; the reverse switch understates equally. Token *counts* stay correct; only the USD figure is wrong. **Fix:** record per-(provider,model) day totals in the budget, or price only the current model's portion.

**F-A5-P2-19 — Budget is in-memory only: any daemon restart resets every chat's daily spend.** `internal/budget/budget.go:27-31` — documented as deliberate ("a rate control, not billing"), but the consequence is a bypass: the daemon was killed by a VM restart on rc7 and restarts via `/restart` (owner-only) or any crash, and every chat's counter resets to zero. A chat at 100,000/100,000 gets a fresh 100,000 after a restart, with nothing in `/usage` or the log recording the reset. **Fix:** persist `usage` atomically (write-temp + rename, like the session store) and reload on start; or at minimum log the reset.

**F-A5-P2-20 — Resolve-vs-expiry race: a tap landing exactly at the deadline can be "approved" to the user while the tool is denied (and the card can end up saying Expired).** `internal/permissions/gate.go:451-478` — `Check`'s `select` has both `case res := <-pr.ch` and `case <-timer.C`. When a tap arrives in the same instant the timer fires, Go picks a case at random. `Resolve` (`gate.go:518`) deletes from `pending` and sends to the buffered channel, returning `true` — so `handleApprovalCallback` (`cmd/oriond/main.go:401-408`) logs "resolved approved=true", edits the card to "✅ Approved — running it now", and answers the tap "Approved", while `Check` took the timer branch, fired `onExpire` (card edited to "⏰ Expired"), and denied the tool with "approval timed out". Two edits then race for the final card text. Double-resolve itself is safe (`Resolve` deletes first; a second tap correctly gets "expired"). Window is milliseconds wide (tap must land within ~ms of the 90 s deadline), hence P2, not P1. **Fix (one-line-class):** in the timer branch, re-check under the gate mutex whether the request was already resolved (e.g. have `Resolve` record the outcome and let the timer branch prefer a delivered result), or drain `pr.ch` non-blockingly before firing the hook.

**F-A5-P2-21 — Resolved approval card keeps its live buttons (same defect class as the rc8 expiry bug, on the success path).** `cmd/oriond/main.go:408` — after a successful tap, the card is edited with plain `gw.EditMessageText` (no `reply_markup`), while the expiry path uses `EditMessageTextMarkup` with an empty keyboard (`main.go:344`). The codebase's own premise for building `EditMessageTextMarkup` (`internal/messaging/telegram.go:~890` doc: "pass an empty InlineKeyboardMarkup to REMOVE the keyboard… without it the dead card keeps live-looking buttons") is that omitting `reply_markup` leaves the keyboard in place — so by that same premise the *resolved* card also keeps live Approve/Deny buttons. A second tap then shows only a transient "expired" toast, exactly the confusing UX the hotfix was meant to kill. (Bot API behaviour was not conclusively established from public sources; grounded in the codebase's own assumption — needs a live check.) **Fix (one-line safe fix):** use `EditMessageTextMarkup` with the empty keyboard for the outcome edit too. Regression test: extend `TestApprovalCallbackRoundTrip` to assert the outcome edit carries `"inline_keyboard":[]`.

**F-A5-P2-22 — Logging gaps: not *every* prompt/tap/outcome logs with the request ID.** `internal/permissions/gate.go` `Check`: when the prompter *fails* (send error), it returns "denied: could not ask for approval" with **no log line at all** — a failed card send is silent, indistinguishable from "user never answered". `cmd/oriond/main.go:371-373`: a tap with unparseable callback data returns "Unknown button." with **no log line**. `cmd/oriond/main.go:344,408`: both card-edit calls are `_ =`-swallowed with no error logging — an edit failure (e.g. message deleted, the case the code comments anticipate) leaves no trace. The prompted-path logging itself is present and does carry the request ID, so the coordinator's "every prompt/tap/outcome logs" is true for the happy path, with these three silent paths as exceptions. **Fix (one-line fixes):** log the three sites.

**F-A5-P2-23 — `/usage` cost prices only the prompt/completion/subagent split; tokens outside the split are unpriced.** `internal/cost/cost.go:171-177` — `EstimateTotals` rebuilds `TotalTokens` as `prompt+completion+subagent`, ignoring the provider-reported total. If a provider reports `TotalTokens > Prompt+Completion` (e.g. cached-token accounting), those tokens are silently unpriced. `budget.go` acknowledges the split "need not sum to Total". Low impact with current providers; note only.

### Skills + validation (F-A5-P2-24 … P2-27)

**F-A5-P2-24 — Skill description is injected verbatim into the system prompt on every turn, before the skill is ever invoked.** `internal/core/skills.go:92-130` (`skillSection`) writes `s.Description` straight into the system prompt; `internal/skills/skills.go:240-270` takes the first paragraph line as the description with no sanitising. A malicious skill therefore gets up to 200 runes of system-prompt text on *every* turn, even if never invoked — unlike the body, which is lazy-loaded. Proof (scratch-copy test): description present verbatim in `req.Messages[0].Content` on call 1. **Fix (small):** quote/delimit the description in `skillSection` (e.g. `"name": "desc"` with newlines/control chars stripped) + regression test.

**F-A5-P2-25 — `## Tools` heading variants silently fail open to unrestricted.** `internal/skills/skills.go:300-312` recognises only an exact (case-insensitive) `## Tools` heading. `## Tools:`, `## Allowed Tools`, `## Available Tools` all parse to `Tools=nil`, and `internal/core/skills.go:197-212` treats nil as "any tool may be used" — the footer even tells the model so. A skill author intending a restriction silently gets none. Proof (scratch-copy test): all three variants yield `Tools=[]`; control exact heading yields `[echo]`. **Fix (one-line-class):** normalise the heading in `parseSkill` (strip a trailing `:`, accept `allowed/available tools`), and ideally log/warn when a file contains a Tools-like heading that was not recognised.

**F-A5-P2-26 — Skill discovery follows symlinks out of the skills dir.** `internal/skills/skills.go:151-190` (`LoadDir` + `parseFile`) uses `os.Open` with no `Lstat`/`EvalSymlinks` check, unlike `file_read` which refuses symlinks (`internal/tools/files.go`). A `.md` symlink inside `~/.orion/skills/` pointing anywhere on disk is loaded as a skill. Proof (scratch-copy test): symlink `evil.md -> /tmp/.../outside.md` ("# Smuggled") loads: `LoadDir loaded=1`, `Get("Smuggled")` succeeds with the outside content. P2 not P1 because it requires write access to the skills dir (where an attacker could write a `.md` directly); it matters because it defeats the documented "loads only from the data dir" guarantee, e.g. for a skills dir populated by a sync/checkout that preserves symlinks. **Fix (small):** in `LoadDir`, `Lstat` each entry and refuse symlinks (or `EvalSymlinks` + require the resolved path to stay under the skills dir) + regression test.

**F-A5-P2-27 — Central validation is top-level only: `[]string` enums are silently dropped, and nested schemas / `minimum` / `maximum` / `pattern` are never enforced.** `internal/tools/validate.go:142` — enum is checked only if `schema["enum"].([]any)`; a Go-built definition using `[]string{...}` silently imposes no enum. `validate.go:90-120` checks only top-level `properties`/`required`; nested `items`/`properties`/`required` (e.g. `todo_write`'s `todos[].content/status`, `internal/tools/planning.go:473-495`) are ignored. `minimum`/`maximum`/`pattern`/`minLength` are never read at all, though schemas declare them (`shell.go:169-170` timeout 1–120, `web.go:388-389`, `526-527`). Proof (scratch-copy tests): enum `[]string{"a","b"}` with `{"mode":"c"}` was **accepted and the tool ran** (control `[]any` correctly rejected it); nested `{"todos":[{"wrong":1},{}]}` (both required fields missing) was **accepted**. Mitigating (why P2): built-ins re-check in `Execute` — shell timeout rejects out-of-range (`shell.go:193-198`), web fetch/search reject (`web.go:421-426`, `555-561`), grep/glob clamp (`search.go:204-212`, `550-558`), `todo_write` re-validates content/status (`planning.go:520-534`). So today this is a defence-in-depth gap plus a trap for any future tool (or MCP tool, which has no second layer) that relies on the validator alone. **Fix (small-to-medium):** accept `[]string` (and numeric-enum normalisation — `reflect.DeepEqual(float64, int)` also mismatches) in `validateValue`, and recurse into `items` + nested `properties`/`required`; add regression tests for each.

### Search + planning (F-A5-P2-28 … P2-36)

**F-A5-P2-28 — Grep `include`/`exclude` not applied to symlinked files.** `internal/tools/search.go:277` (grep walk): the symlink branch appends the resolved target without the `Include`/`Exclude` checks applied to regular files just below it. Proof: tree with `sub/real.txt` containing `NEEDLE_SYM`, plus `link.md` → `sub/real.txt`; `grep {"pattern":"NEEDLE_SYM","include":"*.go"}` returned the `.md` file's line. Filter bypass only (content was inside the root); no confinement break. **Fix:** apply include/exclude to the link name before appending.

**F-A5-P2-29 — Grep `.git` skip bypassed via symlink into `.git`.** `internal/tools/search.go:280-286` skips `.git` dirs in the walk, but the symlink branch (`:277`) only checks `within(target, root)` + `inSensitiveDir` — a link to a file *inside* `.git` is read. Proof: `link.txt` → `<root>/.git/config` containing `SECRET_GIT_NEEDLE`; grep returned `.git/config:2: SECRET_GIT_NEEDLE`. No privilege gain vs `file_read` (which can read `.git/config` directly), but it contradicts the tool description ("Binary files and .git are skipped"). **Fix:** also skip symlink targets under any `.git` directory.

**F-A5-P2-30 — Hardlink escape (shared with `file_read`, conditional reachability).** Grep (and `file_read`) cannot distinguish a hardlink inside the root to a sensitive file outside it — no device/inode/ownership check anywhere on the read path. Proof: hardlink inside root → secret outside root; grep returned `HARDLINK_NEEDLE secret`. Reachability: planting needs a write primitive outside the roots. Sandboxed `shell_exec` cannot (chroot, cwd `/work`, no `~/.orion`); unsandboxed shell/CLI could — `ln` is only blocked when the *link path* is a system target (`security.go:868`), the source operand is never checked. **Fix options:** refuse files whose nlink>1 outside expected cases, or check inode ownership against the root; at minimum verify `fs.protected_hardlinks` is on. P2 because sandbox-ON (live config) blocks the plant.

**F-A5-P2-31 — Grep has no total-bytes cap (no-match scan can read ~10 GB).** Scan cap is 10k *files* (`maxGrepFilesScanned`), each read up to 1 MB — worst case ~10 GB, bounded only by the 120 s tool ctx. Proof: 50×1 MB no-match files took 1.68 s (linear; 10k×1 MB extrapolates to ~5 min, cut off by ctx). **Fix:** cap total bytes scanned per call (e.g. 32 MB) with a footer note, as the file-count cap already does. Related nit: a file >1 MB is silently searched only in its first 1 MB (footer does disclose this).

**F-A5-P2-32 — Grep output size: structural max ~10 MB in-memory before the registry cap.** 500 matches × (1 + 2×10 context lines) × 1000 runes/line ≈ 10 MB. Proof (single file): 500 matches spaced 25 lines apart, 1000-rune lines, `context_lines:10` → 959,226 bytes output (limited by the 1 MB/file read cap; multi-file reaches the ~10 MB bound). Mitigated at the model boundary by the 256 KiB `Registry.Execute` cap (`caps.go:26`, `registry.go:232`), so this is memory/CPU waste, not a context flood. Same class: `task_list` returns up to 500 tasks × ~8 KB of fields ≈ 4 MB JSON, also only capped by the registry. **Fix:** cap total rendered lines (e.g. `maxMatches × (1 + 2×context)` → also cap context *bytes*), or cap `task_list` output with pagination.

**F-A5-P2-33 — Planning: cross-process lost update (daemon + CLI share `~/.orion`).** The mutex only serialises *in-process* load-modify-save; `atomicWriteFile`'s rename does not fix the read-modify-write race across processes/stores. Proof: two `PlanningStore`s on one data dir, overlapped load → both append → both save: final list contained `task_overlap2` but **`task_overlap1` vanished**. **Fix:** `flock` the state file (or a lockfile) around load-modify-save. In-process concurrency is correctly handled (single `s.mu`, verified by code).

**F-A5-P2-34 — Planning state files follow symlinks on load → cross-chat read if one is planted.** `internal/tools/planning.go:253` (`loadTodos`) and `:305` (`loadTasks`) use plain `os.ReadFile`, which follows symlinks. Save is safe (rename replaces the link itself). Proof: replaced `chats/222/tasks.json` with a symlink → `chats/111/tasks.json`; chat B's `task_list` returned chat A's `"A secret task"`. Reachability: planting requires write access to `~/.orion/chats` — not model-reachable via file tools (confined to wd+tmp) or sandboxed shell, so this is defence-in-depth, not a live exploit. **Fix (small):** Lstat the state file and refuse symlinks on load (reuse the `readFileBounded`/O_NOFOLLOW pattern); same for a symlinked `chats/<id>` dir, which `MkdirAll` would follow on write.

**F-A5-P2-35 — Subagent children silently lose all planning state (doc claim is false).** `internal/tools/planning.go:16-20` claims "Subagent children inherit the same context, so a child planning for a chat lands in that chat's files". False on the daemon path: `newChildRegistry` (`app/subagent.go:113`) builds a *fresh* `DefaultRegistry` with a fresh in-memory `PlanningStore`; `SetDataDir` is only ever called on the parent registry (`app.go:130,293`). The child inherits `ApprovalContext` (chat id) via ctx, so it lands in an ephemeral per-child mem bucket (`chat:<id>`), discarded when the executor returns — parent never sees the child's todos/tasks, and vice versa. Fail-closed security-wise (child cannot read parent's plan), but a silent data-loss / broken-contract bug. **Fix:** pass the parent's `PlanningStore` (or its data dir) into `newChildRegistry`. Needs a regression test: spawn child → child `task_create` → parent `task_list` sees it (or assert the intended isolation explicitly if the loss is by design — then fix the header comment instead).

**F-A5-P2-36 (grouped, planning durability/validation, minor) —** `atomicWriteFile` (`files.go:347`) fsyncs the file but never fsyncs the directory after rename: safe against process crash, not OS/power loss. Add dir fsync. `loadTodos` does not validate statuses (unlike `loadTasks`, which rejects duplicate ids / unknown statuses); a hand-edited `todos.json` with status `"done"` loads silently and renders as pending. `loadTodos`/`loadTasks` read the whole file with no size cap (a planted huge `tasks.json` loads unbounded into memory) — planting requires fs access, so low. Single-file grep on a FIFO inside the root blocks up to the 30 s `readFileBounded` timeout (one leaked goroutine); `file_edit` pre-checks regular-file, grep's single-file branch does not. Dead code (not a bug): the symlinked-directory branches in grep (`search.go:262`-ish, `d.IsDir() && symlink → SkipDir`) and glob are unreachable — `WalkDir` Lstat-reports a symlink-to-dir with `IsDir()==false`, so dir symlinks are handled by the file branch (which is why `TestGrepSymlinkEscapeSkipped` still passes).

Hook env: `tools.ScrubEnv` shared with `shell_exec` (drops `ORION_*`, `*KEY*`, `*TOKEN*`, `*SECRET*`, `*PASSWORD*`, `*AUTH*`, credential-bearing proxy URLs); only `ORION_HOOK_EVENT`/`ORION_TOOL_NAME` added. MCP config/trust: `LoadConfig` reads only `<DataDir>/mcp.json`; 1 MiB cap; server/tool names must match `^[A-Za-z0-9_-]+$`; command must be absolute or a bare PATH name (relative paths with a separator refused); args as argv, never through a shell. MCP env: scrubbed base + operator-explicit per-server `env` overlay + `ORION_MCP_SERVER` appended last. MCP naming: `mcp__<server>__<tool>` distinct from built-ins; manager dedupes identical full names; `Registry.Register` rejects duplicates. Every `mcp__` tool is `ClassNetwork` and needs approval when a gate is installed; results pass through the central registry redact+truncate choke point; schema validation runs in `Registry.Execute` before tool code; subagent children get **no** MCP tools and no skill tool; `CallTool` bounded by the 120 s per-tool context; `Close` idempotent, SIGTERM-then-SIGKILLs the process group, reaps; malformed JSON-RPC lines dropped; server `sampling` requests refused, `roots/list` returns empty roots, `ping` answered; non-text content blocks summarised, never passed through raw; no restart loop.

**Cost / budget (worker 4):** unknown (provider, model) returns `false` → `/usage` prints "unknown", never $0; price table versioned (`2026-11-13`, shown in `/usage`); matching is exact after lowercase/trim — no prefix matching, so no cheap-model-name spoof by prefix. Subagent attribution, when the result *is* fetched: no double-count (`finishTurn` adds subagent tokens once, `takeSubagentUsage` resets the accumulator; `delivered` guard charges once). Budget on both daemon paths (`oriond` and `orion daemon`) enforces the budget — the rc8 follow-up is genuinely closed; `/retry` goes through the same `runTurn` and is budgeted. Budget reset semantics: UTC calendar day, reset on access, `ResetAt` = next UTC midnight, shown in `/usage`. Over-budget turns are refused *before* the provider is called, returned as a plain "⏸ Daily token budget reached…" reply, not an error; spend is still recorded even for failed turns. Approval double-resolve / stranger taps / sender check: `Resolve` deletes-then-delivers (second tap gets "expired"); stranger taps refused without touching the pending request; non-allowlisted callback senders dropped with a log line. Expiry hook safety: read once outside the mutex, network edit in a goroutine with a background context, `cards.take` guarantees the edit runs once, failed edit cannot fail the turn. CLI path (`orion run` / `orion chat`) has no budget check — by design, not a bypass: the CLI has no chat context, the operator is local, and the gate/budget docs scope both to Telegram-driven turns (parent to confirm that design intent stands).
